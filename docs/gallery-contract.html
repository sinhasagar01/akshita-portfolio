Gallery — the lightbox

The chosen direction, complete. Dense masonry, a full-bleed preview with a filmstrip, and filters that drive the browse order inside the overlay. Click any tile — arrows, ← → and Esc all work, and swipe works on a touch screen.

⚠ Three things to settle before either is built, and the third is the largest. Where the images live and how they are managed — the brief says keep it flexible, and that is right, but it decides whether this is a content collection like the blog, an upload surface like the studio's, or a folder plus a manifest. Whether an item can be a case study — "Projects" as a filter overlaps the work section, and two places showing the same thing is the duplication this project keeps deleting. And what the preview does about images the site does not own, if any are ever client work.

⚠ This file is authoritative about the layout, the overlay and its controls — not about the images or the data. The tiles are generated SVG so it renders standalone; the item shape (title, kind, width, height, description, tags) is the contract, and where those live is the first thing to decide.

Photographs, drawings, and the odd product study that never became a case study. Mostly taken before 7am or after midnight.

The image gets the whole screen, which is what a photograph wants — and the filmstrip makes twelve items feel browsable rather than sequential. Cost: the dark chrome is a second visual language on a site that themes everything, and the metadata rail is fixed-width, so a long description scrolls inside a column while the image stays put.

⚠ What both mocks are dishonest about, stated rather than discovered later. These images are generated SVG and weigh nothing — a real gallery is the heaviest page on the site by an order of magnitude, and every claim about "smooth" is a claim about bytes, decode time and layout stability rather than about transitions. Masonry with columns reflows on load unless every intrinsic size is known up front; the real build needs width and height per item, content-visibility, and a decode strategy. None of that is visible in a mock, and all of it decides whether the result feels premium.
